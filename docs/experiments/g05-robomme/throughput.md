# G05 四卡训练：从低利用率定位到具体算子

在 4 × RTX 4090 上训练 RoboMME 的同一份 G05 时，每卡 batch 2、全局 batch 8。GPU 利用率表示采样窗口里有 kernel 在执行的时间比例，通信等待也可能被算作忙碌；比较训练效率用每秒处理的训练窗口数。

**定位。** 原实现的第 1,280–1,536 步共 471.96 秒，含相同频率的验证和保存，即 4.34 窗口/秒。四卡并行时用 `nvidia-smi dmon -s pucmt -d 1 -c 42` 连续采样，GPU 0–3 的 SM 利用率中位数分别为 12.5%、14%、14%、13%。在另一项独立测试中，4 张卡用现有 NCCL 配置依次归约 53 个 25 MiB 的 FP32 缓冲区，五次中位数 0.173 秒。这是近似梯度体积的通信实验，不是从整步耗时中直接扣除的分项。

**同一真实批次、一个变量。** 从第 1,536 步的相同参数出发，分别在同型号单卡上跑相同的两个窗口和相同的扩散噪声。前向、反向、优化器间用 CUDA 同步计时；使用零学习率，不改正式权重。每个实现独立运行 10 步，取最后 8 步的中位数。不同列各自取中位数，总时间不一定等于列之和。

| 线性注意力实现 | 取下一批 (ms) | 前向 (ms) | 反向 (ms) | 裁剪＋优化器 (ms) | 整步 (ms) | 抽样梯度与原实现的余弦相似度 |
|---|---:|---:|---:|---:|---:|---:|
| G05 原生 PyTorch 回退 | 10 | 690 | 661 | 22 | 1376 | 1 |
| PyTorch 批量三角求解（实验对照） | 9 | 520 | 488 | 22 | 1050 | 0.99948 |
| 上游 FLA 0.6.0 | 10 | 310 | 222 | 21 | 567 | 0.99902 |

18 层 GatedDeltaNet 在一个联合训练批次的前向里调用了 36 次分块线性注意力。原生实现用 Python 循环按行更新 32 行块；前向中这些函数的主机侧累计耗时由 446 ms 降至 64 ms（包括其中的等待，不是纯 GPU kernel 时间）。单卡 2.43 倍是整批计算对照，不等同于四卡加速比。采用的是 [FLA 上游算子](https://github.com/fla-org/flash-linear-attention/blob/v0.6.0/fla/ops/gated_delta_rule/chunk.py)，由 G05 自带的后端选择加载；无需修改上游源码。此测试的 FLA 快路径也包括 G05 随之启用的 fused RMSNorm。三角求解仅用于定位，不用于训练或评估。

**复现。** 先按[本实验 README](README.md)设置 `ART`、`EXP`、`PY`、`PYTHONPATH`。在已有 G05 环境下把固定版本装到独立目录，不升级训练机的 PyTorch 和 Triton。下面的单卡测试应在该卡空闲时进行，使用相同的核心增量权重；若无本机的 1,536 步快照，可用自己保存的同一个 checkpoint 来比较两种实现。

```bash
uv pip install --python "$PY" --no-deps --target "$ART/fla6" 'fla-core==0.6.0'
delta="$ART/perf-1536/delta.pt"
CUDA_VISIBLE_DEVICES=0 "$PY" "$EXP/bench_step.py" "$ART" "$delta"
CUDA_VISIBLE_DEVICES=0 PYTHONPATH="$ART/fla6:$PYTHONPATH" "$PY" "$EXP/bench_step.py" "$ART" "$delta"
```

本机用 PyTorch 2.7.1+cu128 / Triton 3.3.1。训练和对比脚本会打印实际加载的 kernel 名称；正式命令使用 `--require-fla`，依赖缺失时直接报错，避免悄悄恢复慢速实现。首次 FLA/Triton 编译在单卡对照中约 120 秒，包含在冷启动、不计入稳态结果。原定位实验用两个预取 worker 测量取批等待。正式训练与复测脚本直接读取缓存窗口，避免 CUDA/Triton 初始化后再 fork。训练日志每 25 步记录四卡合计的 `samples_s` 和 rank 0 每步的 `input_wait_ms`，并在验证后重置计时。每次续训都在相同的 128 个留出窗口上重新评分，超过 1% 的偏差会在做优化更新前中止。

**正式切换。** 第 1,536 步恢复模型和 AdamW，同一留出集复测为 2.265298（原值 2.265789，相差 0.022%）。对照批次上 CE 为 2.47738 → 2.48194，FM 为 0.09289 → 0.09295，梯度裁剪前范数为 5.4655 → 5.5408。四个 rank 均从独立目录加载 FLA。训练每卡仍为 2 个窗口，学习率、30K 目标、离线验证及原生测试协议不变。四卡恢复后的 42 次采样，GPU 0–3 的 SM 利用率中位数为 22%、24.5%、21.5%、23.5%，均值为 45.2%、40.7%、32.7%、46.0%；其上下波动不等于数据加载器停顿。

**四卡最终同口径计时。** 比较两个相邻验证点的落盘时间。每段均为 256 个真实更新、2,048 个训练窗口，包含一次相同的 128 窗口验证和 checkpoint 保存；不含切换、冷编译或仿真。

| 后端 | 优化步区间 | 墙钟秒 | 秒/步 | 训练窗口/秒 |
|---|---:|---:|---:|---:|
| 原生 PyTorch | 1,280 → 1,536 | 471.96 | 1.844 | 4.34 |
| FLA 0.6.0 | 1,792 → 2,048 | 194.02 | 0.758 | 10.56 |

本机实测吞吐为原来的 **2.43 倍**，同样步数用时减少 58.9%。在后一段中，不含验证的日志区间吞吐中位数为 11.71 窗口/秒，rank 0 等待输入中位数为 15.5 ms/步。第 1,792 与 2,048 步的联合留出 loss 分别为 2.248296 和 2.220855。这些数字适用于这台机器、这个 batch 和这四项数据；评测成功率另行统计。

## 第二轮：数据还是同步？

第 2,816 步，同一模型、FLA 0.6.0、4 × 4090、全局 batch 8。正式任务从 2,048 到 2,816 步（含 3 次验证和写盘）实测速率为 **10.40 窗口/秒**。参考 [ResearchBoost-Agent 固定版本](https://github.com/DAGroup-PKU/ResearchBoost-Agent/tree/f6182090511f0b317262c42025e55cf3c940880b) 的[分层分析](https://github.com/DAGroup-PKU/ResearchBoost-Agent/blob/f6182090511f0b317262c42025e55cf3c940880b/skills/train-opt-tiered-profiling/SKILL.md)及[通信优化清单](https://github.com/DAGroup-PKU/ResearchBoost-Agent/blob/f6182090511f0b317262c42025e55cf3c940880b/skills/train-opt-action-ladder/SKILL.md)，区分诊断上限和可以用于训练的优化。

每个 rank 取四个不同的真实双样本批次，固定图像增强和扩散噪声，均使用零学习率防止测速改变权重。每项 10 步，首 2 步不计，正序和反序各一次；步末等待各卡完成，表内是每步最慢 rank 的时间，每轮取中位数。端到端速度另看正式训练日志。

| 诊断或候选设置 | 正序 ms/步 | 反序 ms/步 |
|---|---:|---:|
| 原四卡 FLA | 643.4 | 663.2 |
| 批次预存 CPU | 629.6 | 635.8 |
| 批次预存 GPU | 621.5 | 644.0 |
| 禁用梯度同步（仅诊断） | 495.6 | 480.0 |
| 跳过动作专家不读取的递归缓存 | 635.4 | 610.8 |
| 普通注意力切 PyTorch SDPA | 652.4 | 628.7 |
| 同时跳过缓存和切 SDPA | 624.6 | 614.5 |

四卡中最慢的输入准备约 14.5 ms，H2D 约 1 ms；两个缓存对照均仅节省约 3%。禁用梯度同步平均节省约 166 ms（含卡间等待），该对照不能用于正式训练。基线 rank 0 的前向组件 CUDA event 中位数：视觉塔 31 ms，视觉语言主干 110 ms，动作专家 64 ms；这些是前向子区间，不与反向或各 rank 分项相加。缓存和 SDPA 候选未通过预定门槛：须在两轮都至少快 5%，因此未采用。

可迁移的是定位和验收方法，而不是其他机器的倍速。例如 [Faster-Motus](https://github.com/AI4AI-for-Anything/Faster-Motus#what-changed) 消除的是 DeepSpeed ZeRO hooks 的重复遍历及嵌入文件的重复读取；本轮 G05 为原生 DDP，RGB 已按轨迹 mmap。

## 第三轮：让梯度同步与反向计算重叠

本机 GPU 0/1 与 2/3 分属两个 NUMA 节点，四卡均为 PCIe Gen4 ×16。`nvidia-smi topo -p2p r` 和 `-p2p w` 对每一对 GPU 均返回 `CNS`。每步需对 343,294,964 个 FP32 梯度元素求平均，逻辑梯度大小约 1.28 GiB。四个 rank 都使用全部 121 个可训练张量。基于这些实测条件，对照 DDP 的两个设置：关闭逐步遍历计算图查找未使用参数，启用梯度桶视图；再比较 25 MiB 与 64 MiB 的桶容量。两个选项一起测，不能把组合收益单独归给其中之一。[PyTorch DDP 参数说明](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html)

从第 3,072 步的同一份模型和 AdamW 状态出发，按「基线、25、64、64、25、基线」顺序复测。每项先预热 4 步，再采 3 组，每组连续跑 4 步，在组首、组尾同步。每组取四卡最慢的墙钟时间，除以 4，各轮报告三个结果的中位数。测速使用零学习率；独立的数值对照恢复 AdamW 状态，用相同数据、噪声以及非零学习率 `2e-6` 更新一次。第一次启动测速时 cuBLAS 无法分配句柄；下表是以相同可扩展分配器设置和预热方式完整重跑的结果。[原始计时和验收门槛](result-ddp.json)

| DDP 设置 | 正序 ms/步 | 反序 ms/步 | 相对基线吞吐（正序 / 反序） |
|---|---:|---:|---:|
| 原设置 | 683.0 | 761.7 | 1.00× / 1.00× |
| 梯度桶视图、全部参数参与，25 MiB | 523.6 | 552.3 | 1.30× / 1.38× |
| 梯度桶视图、全部参数参与，64 MiB | 539.1 | 578.2 | 1.27× / 1.32× |

两种候选均通过「正、反序吞吐分别至少提高 5%」及数值门槛，选择两轮均更快的 25 MiB。对四个 rank 的全部 121 个张量逐元素核对，25 MiB 的最差单张量梯度相对 L2 误差为 `8.45e-8` 以内，更新后权重最大绝对差为 `7.46e-9` 以内，同一输入的 loss 差为零。

正式续训在 128 个固定留出窗口上复测第 3,072 步，保存值与恢复值均为 `2.208931`（日志精度）。第 3,073 步在学习率 `1.87772934e-5` 下完成了四卡更新，联合 loss 为 `1.738201`，梯度范数为 `2.846634`。

复测正式训练时，按[训练说明](README.md)分别在同一完整断点的两个独立副本运行四卡 `core.py --resume`。保留相同的数据、总步数、FLA 版本、GPU 顺序与验证频率，仅在优化组加入 `--ddp-bucket-mib 25`。比较相邻的两个验证点落盘时间，排除第一次启动和恢复验证。每 256 步有 2,048 个训练窗口，吞吐等于 2,048 除以两次落盘的时间差。
