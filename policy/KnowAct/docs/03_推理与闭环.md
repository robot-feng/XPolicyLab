# 03｜推理状态、BAR16 与闭环执行

## 1. XPolicyLab 入口

`policy/KnowAct/model.py` 继承原版 `XPolicyLab.policy.G05.model.Model`：

- 复用原 G05 观测解析、相机图像处理、状态打包、动作反归一化和机器人动作输出。
- 只替换内部 G0.5 root / checkpoint 与 Native Context 推理路径。
- Native Context 维护 `_native_states[env_key] = (InferenceState, plan_id, sent_steps)`。
- batch 内 env key 必须唯一；同一批次逐环境计算并在整批成功后原子发布状态。
- `reset()` 同时清除原 Adapter 状态和 KnowAct Native Context 状态。

因为原版 G05 与 KnowAct vendored source 都导入 `g05`，两者必须在独立 Python 进程和环境运行。

## 2. `generate_action()` 的调用顺序

```python
state = policy.append_context(
    state,
    samples,
    pixel_values,
    executed_steps=previous_receipt_steps,
)

# 可选：同一 state 上先生成语言
state = policy.generate_text(state, stop_token_ids=[eov_id])

# 再用同一 state 生成 BAR16 动作
result = policy.generate_action(
    state,
    samples,
    action_dim_is_pad=action_dim_is_pad,
    action_source="ar",
)
```

实际 `PolicyInferencer.infer_stream()` 负责调用上述接口，并复用原 Processor / postprocess。

## 3. BAR16 语义

- `block_size=16` 是新训练 checkpoint 的动作 Token 块宽。
- 一次 BAR Forward 并行预测一个 16 Token 块；块与块之间按自回归顺序生成。
- 16 个 Token 不等于 16 个机器人控制时刻。
- 动作 Token 仍由原 G0.5 ActionCodec 编码；分组标记、RVQ 代码、PAD / EOS 等由原 BARBuilder / ActionCodec 布局决定。
- 当前 Native Action Layout 要求 `block_wise_autoregressive=true`、BAR block size=16、`ar_block_num=0`、固定 grouped layout。
- 不允许只在推理时把已有 checkpoint 的 block size 改成16；不同块宽必须有匹配训练布局和 checkpoint。

## 4. 32 步预测、16 步执行

当前 RoboDojo 配置的 action horizon 为32。KnowAct 推理会完整生成并解码32步动作，但默认只把前16步发给环境：

1. `G05Policy.generate_action()` 生成完整动作 Token 序列。
2. 原 ActionCodec 完整解码为32步连续动作。
3. `Model` 的 `action_steps` 设为 `KNOWACT_REPLAN_STEPS`。
4. XPolicyLab Adapter 格式化输出时只返回前16步。
5. `deploy.py` 再做一次防御性 `_limit()`，确保不超过执行间隔。
6. 环境执行实际返回的动作数；episode 提前结束时，实际步数可能小于16。

原版 G05 `deploy.yml` 默认 `action_steps=16`。公平对照应匹配相同实际下发步数，而不只是相同预测 horizon。

## 5. 执行回执协议

下一轮 observation 可携带：

```python
{
    "__knowact_execution__": {
        "plan": 3,
        "steps": 12,
    }
}
```

字段语义：

- `plan`：上一轮下发计划的序号，必须与待确认计划序号一致。
- `steps`：环境确认已经应用的控制命令数量，范围 `0..sent_steps`。
- 它不是关节传感器测量值，也不是机器人真实轨迹；真实状态从当前 observation 的 proprio / image 进入模型。

状态事务：

1. 新观测到达后，检查 receipt 是否缺失、重复、过期或超范围。
2. 如果有 pending action，只取已应用前缀。
3. 由于当前原 ActionCodec 不是严格时间因果解码器，不直接切片神经 Token；将已执行连续动作前缀 hold-pad 到原 horizon，再用原 Processor / Codec 重新编码。
4. 追加新的真实观测与 receipt 文本。
5. 生成新的完整动作计划。
6. 只有动作解码、shape 检查、有限值检查和 Adapter postprocess 全部成功后，才提交候选状态。
7. 失败时旧的已提交状态保持不变。

`steps=0` 表示上一计划没有动作被确认应用：丢弃 pending proposal，不把该计划写入已执行动作历史。

## 6. 为什么不能边生成边执行部分 Codec 输出

V7 的小配置原生 Codec 扰动测试显示：修改较晚的合法神经代码会改变更早的连续动作前缀。因此不能假设“已经生成的部分 Token 对应的连续动作永远不变”。

当前安全语义是：**完整解码一个 Action Chunk，再执行其中的前缀，收到新观测后重新规划。**

这不是 chunk 内异步打断，也不是 NAT 式因果 Codec。要实现任意时刻边生成边执行，必须先用正式预训练 ActionCodec 做 prefix perturbation 测试；若不满足，再独立研究因果 Codec。

## 7. 多环境与 reset

- 每个 env 使用稳定 key（`env_idx` / `env_id` / `env_index`）。
- batch 中 key 不可重复。
- 每个 env 的 `InferenceState` 独立；一个环境失败不能提交同批其他环境的部分状态。
- receipt 的 plan ID 必须严格递增。
- Episode 结束或开始新 Episode 时调用 `reset()`。
- `KNOWACT_KEEP_HISTORY=false` 是同 checkpoint 的清空历史消融，不等同于单轮训练 checkpoint。

## 8. 当前闭环限制

- 只在动作 chunk 边界接收新 observation / receipt。
- 不支持执行命令飞行中任意时刻打断 GPU kernel。
- receipt 表示命令已应用的步数，不提供测量轨迹。
- 不支持未确认 pending plan 时再次生成。
- 不支持 FM action source 的 Native Context。
- 没有自动 KV eviction / memory compression；超出 token budget 会报错。
